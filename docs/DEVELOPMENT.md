# 程序开发说明：基于安全 Socket 的智能路口控制系统

> MSE806 Intelligent Transportation Systems · Assessment 2 · 软件部分
> 本文记录这套程序的设计思路、模块结构、关键算法、开发过程、测试与实验，以及演示方法。

---

## 1. 项目目标

| 目标 | 说明 |
|---|---|
| 可靠的通信系统 | 车辆与路口控制器通过 TCP 实时通信（V2I），断线可恢复，坏数据不会让系统崩溃 |
| 智能信号控制 | 固定配时和自适应配时两种模式，并支持救护车信号优先 |
| 真实可测的安全机制 | 防伪造、防篡改、防重放、防冒充救护车、防洪泛，每种都可以开关对比 |
| 可量化的分析 | 每个实验都输出 CSV 数据和 SVG 图表，用于报告的效率和安全分析 |

对应作业的 LO3（开发可靠的软件通信系统）和 LO4（分析评估系统的效率与安全）。

### 3.2 关键设计决策

1. **控制器与网络分离**：`SignalController` 不依赖 socket、线程或真实时钟，时间由调用者传入。
   - 实时服务器传入真实时间（加速时传入模拟时间）。
   - 快速仿真以 0.1 秒为一步传入模拟时间，30 分钟的交通一秒左右就能跑完。
   - 同一份代码既用于实时系统也用于实验，所以实验数据能代表真实系统。
2. **每个客户端独立读写线程，发送队列有上限**：慢客户端会被断开，不会拖慢其他车辆或控制循环。
3. **广播只编码和签名一次**，然后分发给所有客户端，提高效率。
4. **安全可开关**：`--security off` 是故意不设防的对照组，用来证明每项防护确实起作用。

## 4. 通信协议

- 传输：TCP，每个客户端一条连接，默认 `127.0.0.1:9000`。
- 格式：每行一个 UTF-8 JSON 对象；客户端发来的消息最大 4,096 字节。
- 消息外壳（所有消息都有）：

```json
{"v": 1, "type": "POSITION_UPDATE", "sender": "V0007", "ts": 1730000000.123,
 "nonce": "9f2c1a7b3e4d5f60", "payload": {...}, "sig": "HMAC-SHA256 十六进制"}
```

- 签名范围：去掉 `sig` 字段后，按 `sort_keys=True, separators=(",", ":")` 生成规范化 JSON，对它计算 HMAC-SHA256。

| 消息 | 方向 | 用途 |
|---|---|---|
| `REGISTER` / `REGISTER_ACK` | 双向 | 注册身份；回复中带安全模式、信号模式和加速倍数 |
| `POSITION_UPDATE` / `QUEUE_INFO` | 车→路口 / 路口→车 | 每 0.5 秒上报位置；路口告诉车辆前车位置，用于跟车 |
| `CROSSED` | 车→路口 | 通过路口，上报等待时间 |
| `EMERGENCY_REQUEST` / `EMERGENCY_CLEAR` | 救护车→路口 | 请求和解除信号优先 |
| `SIGNAL_STATE` | 路口→全部 | 信号灯状态，每秒 2 次，变化时立即推送 |
| `SNAPSHOT` | 路口→仪表盘 | 每秒 10 次的完整画面数据 |
| `PING` / `PONG` | 双向 | 测量延迟 |
| `HEARTBEAT` | 车→路口 | 保活 |
| `ERROR` | 路口→车 | 错误码：`MALFORMED`、`BAD_SIGNATURE`、`STALE`、`REPLAY`、`RATE_LIMITED`、`UNAUTHORISED`、`NOT_REGISTERED` |

完整说明见 `docs/PROTOCOL.md`。

## 5. 核心算法

### 5.1 信号相位与安全约束
相位固定顺序：`南北绿 → 南北黄(3 s) → 全红(2 s) → 东西绿 → 东西黄(3 s) → 全红(2 s) → …`

**安全约束**：南北和东西永远不会同时非红；每个绿灯之后必须先黄灯、再全红，任何路径都不能跳过。单元测试用 2 小时随机车流加随机救护车请求来验证。

### 5.2 固定配时
每个方向绿灯固定 30 秒。

### 5.3 自适应配时（感应控制）
- 最短绿灯 10 秒，最长绿灯 45 秒，检测区为停止线前 60 米。
- 过了最短绿灯后，满足以下任一条件就结束绿灯：
  - **空档结束（gap-out）**：检测区连续 3 秒没有车，并且对向有车在等；
  - **最长结束（max-out）**：达到 45 秒，并且对向有车在等。
- 对向完全没车时，绿灯可以一直保持。

### 5.4 救护车信号优先
- 救护车在距离停止线 150 米处发出请求。
- 如果本方向已经是绿灯，就保持绿灯，最长 30 秒。
- 如果对向是绿灯，**立即结束**（即使还没到最短绿灯），但仍然先走黄灯和全红，再给救护车方向放绿灯。
- 救护车通过后发送解除请求，恢复正常运行。

### 5.5 车辆运动模型
- 车辆在 200 米外出现，最高速度 13.9 m/s（50 km/h），加速度 2 m/s²，舒适减速度 4 m/s²。
- **跟车**：与前车至少保持 7 米（车长 5 米加 2 米间隔）。
- **黄灯两难区规则**：能舒适停下就停，停不下就通过。
- 等待时间：速度低于 0.5 m/s 的累计时间。
- 越过停止线 20 米算作通过。

## 6. 安全设计

| 威胁 | 防护措施 | 结果码 |
|---|---|---|
| 伪造消息 | HMAC-SHA256 签名，常数时间比较 | `BAD_SIGNATURE` |
| 篡改消息 | 改动任何一个字节，签名都会失效 | `BAD_SIGNATURE` |
| 冒充救护车 | 身份由**验证通过的密钥**决定，不看消息里自称的角色；救护车有独立密钥 | `UNAUTHORISED` |
| 冒用他人身份 | 发送者必须和注册时的身份一致 | `UNAUTHORISED` |
| 重放攻击 | 时间戳 ±2 秒有效，加上每个发送者的随机编号缓存 | `STALE` / `REPLAY` |
| 洪泛攻击 | 每条连接令牌桶限速（每秒 20 条，突发上限 40），10 秒内超限 3 次断开 | `RATE_LIMITED` |
| 伪造信号灯 | 服务器下发的消息用服务器密钥签名，车辆拒收验证失败的消息 | 客户端拒收 |
| 事后追查 | 所有拒绝都写入 `logs/security_events.csv` | — |

服务器处理每条消息的顺序：

```
大小检查 → JSON 与字段校验 → 限速 → 验签（判定身份）→ 时效检查 → 编号查重 → 权限检查 → 注册检查 → 执行
```

先验签、后记录编号，这样未签名的垃圾消息无法塞满缓存。

**已知简化**：
- 所有普通车辆共用一把车队密钥。
- 消息只签名、不加密。
- 依赖时钟同步（演示环境在同一台机器上，所以满足）。

未来可以改用 IEEE 1609.2 风格的证书体系（ECDSA 签名、假名证书），并用 TLS/DTLS 加密。

## 7. 可靠性设计

| 机制 | 说明 |
|---|---|
| 自动重连 | 断线后按 0.5 → 1 → 2 → 4 → 5 秒逐步重试，用同一 ID 加 `resume` 重新注册 |
| 会话保留 | 车辆断线后，服务器保留它的状态 10 秒 |
| 车辆端保护 | 3 秒收不到有效信号，就按红灯处理，停在停止线前 |
| 服务器端降级 | 自适应模式下 10 秒没有车辆数据，自动切回固定配时；数据恢复后切回自适应 |
| 坏数据隔离 | 格式错误或超长的消息只返回错误，服务器继续服务；单条消息出异常也不会影响整体 |
| 慢客户端保护 | 发送队列满或发送超时，就断开这个客户端 |
| 仪表盘重连 | 断线时显示 "Disconnected – retrying…"，并自动重连 |

## 8. 演示功能

### 8.1 一键演示控制面板（`demo_app.py`）
一个窗口内包含：左边路口动画，中间统计数据和安全事件日志，右边设置、按钮和操作日志。
- 设置：安全开或关、固定或自适应配时、车流类型、速度（1×、2×、4×、8×）。
- 按钮：启动或重启、全部停止、派救护车、重启服务器（重连测试）、攻击 A1–A5。
- 操作日志会显示：
  - 每次点击做了什么；
  - 攻击的预期结果和实际结果（绿色 BLOCKED 或红色 SUCCEEDED）；
  - 服务器实时事件（信号优先开始和结束、降级、拒绝记录）。

### 8.2 加速播放
- 服务器使用模拟时钟：`模拟时间 = 起始时间 + (当前时间 − 起始时间) × 倍数`，信号配时按模拟时间运行。
- 车辆从注册回复里拿到倍数，运动按"真实时间 × 倍数"推进；加速超过 2 倍时刷新率提高到 20 Hz。
- 车流生成器把到达时间除以倍数。
- 仪表盘左上角显示橙色 "▶▶ 4× SPEED" 和模拟时间。
- **安全相关的时间（消息时效、限速、会话保留）始终按真实时间**，所以加速不会影响攻击演示的结果。

### 9.2 开发中遇到的问题与解决

| 问题 | 原因 | 解决 |
|---|---|---|
| 车辆停在停止线上后又闯红灯 | 距离等于 0 时被判为"已过线" | 改为距离小于 0 才算过线 |
| 1,000 条畸形消息只有 292 条被记录拒绝 | 同一数据块里出现超长行时，前面的合法行被一起丢掉；测试客户端也没等服务器断开就继续发 | 拆包时先处理超长行之前的完整行，测试端等服务器断开后再重连 |
| 安全关闭时的洪泛攻击被意外断开 | 服务器给攻击者的回复堆满发送队列，触发了"慢客户端"保护 | 写线程改为批量发送；洪泛改用不需要回复的 HEARTBEAT |
| 2,000 条突发洪泛在本机看不出影响 | 本机网络太快，零点几秒就处理完了 | 增加持续 10 秒的洪泛场景 A5s，如实记录两种结果 |
| 仪表盘快照超过 4 KB 上限 | 车辆多时，完整车辆列表很大 | 只放宽"服务器→仪表盘"方向到 64 KB，客户端发给服务器仍限 4 KB |
| 信号丢失测试误判为失败 | 判断条件要求"停在线前大于 0 米"，实际正好停在 0.0 米 | 改为"大于等于 0" |
| 洪泛测试偶发线程异常 | 接收线程还在读时，主线程已经关闭了连接 | 先等接收线程结束再关闭连接 |
| Mac 上仪表盘打不开 | Homebrew 的 Python 没有附带 Tk | 提示安装 `python-tk`；缺 Tk 时给出提示而不是报错 |
| 演示窗口太宽、排队车辆重叠 | 布局和车辆尺寸偏大 | 缩小画布和车辆尺寸（约 7 米一辆） |

## 11. 实验与主要结果

实验命令：`python3 -m experiments.<名称>`，结果在 `results/` 文件夹，完整表格见 `docs/EXPERIMENTS.md`。

| 实验 | 主要结果 |
|---|---|
| 固定 vs 自适应 | 平均等待：低流量 10.6 → 6.4 秒，不对称流量 11.4 → 6.5 秒；高流量均衡 10.7 → 13.0 秒（自适应反而更差，因为绿灯每次都跑满 45 秒） |
| 救护车优先 | 救护车等待从 7–17 秒降到 0 秒；其他车辆平均等待只增加 0.1–0.7 秒 |
| 通信延迟 | 100 个客户端时平均 12.0 ms（安全关）和 15.7 ms（安全开），没有丢包 |
| 加密开销 | 签名或验证约 10 µs；每条消息多约 26 µs、多 73 字节 |
| 可靠性 | 服务器重启后 20/20 辆车约 0.5 秒内重新注册；1,000 条畸形消息全部被拒且服务不断；约 3 秒判定信号丢失并停在线前；10 秒后降级为固定配时 |
| 攻击 | 安全关：A1–A4 全部成功；安全开：全部被拒。持续洪泛时，安全关的正常车辆 p95 延迟 1.45 → 39.5 ms，安全开基本不受影响 |

实验局限：
- 只在本机网络上运行；
- 车辆是模拟的；
- 共用车队密钥；
- 延迟测试中所有客户端在同一个进程里。

## 13. 与原始规格（MVP_SPEC）的差异
